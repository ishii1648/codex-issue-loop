# agent-loop

Use the `agent-loop` CLI as the only control interface. The Skill does not own the Issue loop or its durable state.

## Safe workflow

1. Run `agent-loop doctor --repo <path> --json` before the first start or after configuration changes.
   - Require `schema_version: 1`. If the version is unknown, stop and report that the installed CLI and Skill are incompatible.
   - Require `INSTALL_VERSION_CONSISTENT` when an installed distribution is present. If binary, Skill, or manifest versions differ, do not start the loop.
   - Require `SCHEMA_VERSION_SUPPORTED`. For `SCHEMA_MIGRATION_REQUIRED`, show `agent-loop migrate --json` as a read-only preview and do not start the loop. Apply or roll back a migration only when the user explicitly authorized the version change and every registered loop is stopped.
   - Branch on failed `diagnostics[].code`, not localized `summary` or `detail` text.
   - Present each failed diagnostic with its concrete `remediations`. Do not execute a remediation merely because doctor returned it; every remediation is advisory and has explicit `automatic` and `destructive` fields.
   - Never delete, reset, overwrite state, or change macOS/GitHub/Codex settings as an automatic repair. For `GITHUB_LABELS_MISSING`, preview `bootstrap-labels` first and apply only within the user's authorized repository scope.
2. Run `agent-loop status --repo <path> --json` before mutating loop state.
3. Use `start`, `stop`, or `restart` only for the repository the user named.
4. If status contains a pending request, present that request before starting a new watch. Preserve its request ID, Issue number, question, reason, recommended option, every option ID and label, and whether free text is allowed. In Codex Desktop, ask it as a question that waits for the user's response so question notifications and Activity can surface it; do not finish with a progress-only summary.
5. Otherwise call `agent-loop watch --repo <path> --until-attention --json` once.
6. Do not implement a Codex-side polling loop. The Go watch process combines OS events with reconciliation polling internally.
7. When watch returns `needs_input`, preserve the request ID and all question fields described above, then ask the user. Never merge multiple requests or infer an answer for one request from another.
8. Record the answer exactly once with `agent-loop answer --repo <path> --request-id <id> --message-file -`, passing the answer through standard input rather than interpolating it into a shell command. Confirm with one `status --json` call that the named request is answered.
9. Return to one blocking watch call in the same monitoring task after the answer is recorded. After a task disconnect, Desktop restart, or Mac restart, begin again with `status --json`; re-present any durable pending request before reconnecting watch.

For an ordinary worker `needs_input`, verify that `status --json` shows the same pending request ID and an Issue-local continuation with the saved run, generation, worktree, branch, and session before answering. An answered request may remain durable while another Issue owns root `active_execution`; wait for normal release and never alter the other Issue. Never add ready/running labels, edit state, or submit a second request ID to force progress. After acquisition, verify one higher Issue generation, the same worktree/branch/session, and let the supervisor's launch validation gate the continuation.

For normal Desktop operation, dedicate and pin one monitoring task per repository. Keep the repository path and every `--repo` argument fixed within that task. Do not multiplex repositories in one blocking monitor. OS notifications and Activity are discovery aids; the snapshot and GitHub Issue remain authoritative, and no new Activity item is guaranteed while the Desktop task is disconnected.

For any terminal Issue that may continue, inspect only the canonical snapshot plus current process, worktree, Git, and GitHub state. Event count or ordering is audit evidence, never continuation authority. Run `agent-loop issue plan --repo <path> --issue <number> --json` first and present the suspension, checkpoint stage, evidence, missing evidence, and every action with its eligibility and refusal code.

Use only `agent-loop issue resolve --repo <path> --issue <number> --action resume|retry-stage|adopt-pr|cancel --json` after the operator selects an eligible action. `resume` continues the saved worker/session boundary, `retry-stage` re-enters the saved publish/checks/conflict boundary without rerunning a completed worker, `adopt-pr` accepts only one already-merged same-repository Pull Request matching the saved branch/head/base, and `cancel` moves the Issue to durable `canceled` without execution. The CLI must revalidate the plan in the write transaction and fail closed if the snapshot revision, PID/PGID, pending request, root `active_execution`, worktree, branch, local/remote head, Pull Request, labels, or evidence changed.

A terminal Issue has no root `active_execution`; its `ContinuationCheckpoint` retains the original run, generation, base SHA, workspace, session, result digest, stage, and evidence. A `Suspension` records origin, reason code, recoverability, missing evidence, and allowed actions. Only a successful executable resolution may reacquire `active_execution` with a higher fenced generation. Ambiguous evidence quarantines that Issue alone and permits only `cancel`; it never blocks unrelated queue entries or authorizes provenance synthesis.

Never repair a rejected plan by editing durable state, events, labels, worktrees, or branches. Never infer authority from legacy event shapes or error strings. Scenario-specific v4 fields are accepted only by the stopped-host migration decoder; the v5 runtime rejects them. `watch --until-attention` may continue to return a sticky suspended Issue, so inspect queue capacity separately and do not release another Issue's `active_execution`.

When GitHub reports an authoritative `NOT_PLANNED` close for a terminal `blocked` or `failed` Issue, normal startup, periodic, webhook, or safety-sweep reconciliation may move it to `canceled`. Verify `status --json` contains `github_state_reason: NOT_PLANNED` and cancellation evidence with the previous status, `execution_release_result`, preserved Pull Request identity, and timestamp. A canceled Issue is not sticky `blocked`/`failed` attention. If the target Issue has PID/PGID or root `active_execution`, a pending request, inconsistent ownership, an unknown state reason, or ambiguous Pull Request identity, report the refusal and do not signal processes, discard worktrees, or edit state/labels to force cancellation. An unrelated Issue's root `active_execution` remains owned by that Issue and does not block this convergence.

If a new aggregate validator quarantined a delivery-maintenance snapshot solely because legacy `completed + pull_request_merged` records lack Pull Request number or authoritative head SHA, do not copy backup files or edit JSON manually. Require the repository LaunchAgent to be non-running and first run `agent-loop recover-quarantined-snapshot --repo <path> --backup <exact-status-backup> --dry-run --json`. Present every target's saved Issue/run/branch/URL/old identity and GitHub-verified replacement. Use `--confirm-legacy-merged-identities` only after explicit operator confirmation. The CLI must require the exact recovery marker and managed backup, an otherwise-valid snapshot/event chain in delivery maintenance, no active worker identity, immutable completed records only, and repository-local merged PRs with exact URL/branch/configured base. It preserves both the quarantined snapshot and the recovery marker, records one audit event, and must reject any additional invariant violation, open/fork/missing/ambiguous PR, changed URL/branch/number, running LaunchAgent, or non-exact backup. After recovery, rerun `doctor` and the original typed delivery rollback; never treat this command as a generic corrupt-state restore.

Treat a storage or semantic contract version mismatch as a non-mutating migration requirement, never as corrupt state. If an older release already created an exact revision 1 recovery marker solely for `snapshot semantic contract version <source> does not match <target>`, keep the repository LaunchAgent unloaded and use only `recover-semantic-quarantine --repo <path> --backup <marker-recorded-path> --dry-run --json`. After confirming the exact reason, digest, revision, Issue count, zero worker/lease/pending requests, and optional `next_backup`, use `--confirm-exact-backup` for one step. Repeat only with the returned next backup. When the original snapshot is restored, do not run normal state commands with the new binary; stop every registered repository and run the versioned migration preview/apply. Never copy recovery files or select an unrecorded backup manually.

For worktree retention, run `agent-loop cleanup --repo <path> --json` first and present every candidate, reason, safety flag, recovery source, and purge confirmation token. `cleanup --apply` requires the named repository loop to be stopped and explicit user authorization. Never use `cleanup --apply` for an entry marked dirty, unpushed, open-PR, or unanswered-request; the CLI must also reject it. Use `purge` only for the single Issue the user explicitly authorized, copy the exact confirmation token from the current cleanup preview, and explain that dirty changes are not recoverable. Never infer or synthesize approval for purge.

Confirm the exact repository and impact before `stop`, `restart`, `unregister`, `update`, `migrate --apply`, either rollback, or `uninstall`. Use only a checksum- and attestation-verified release artifact for update. Use only the exact managed backup paths returned by update and migrate for rollback. When rolling back across schema versions, restore the schema backup before the installation backup. None of these commands should delete state, worktrees, or uncommitted changes.

After a global operator update or rollback under per-repository delivery, verify every repository assignment immediately. Each plist program and runtime digest must still match that repository's immutable assignment slot; the global binary update must not change repository assignments. If any mismatch appears, keep affected workers stopped and use only an assignment-aware verified update or a dedicated assignment recovery command—never edit plist or assignment config manually.

For a repository assignment `rollback_failed`, preserve the repository fence and transaction. After fixing the reported cause, confirm the exact repository, no active worker, retained fence, transaction target, and expected generation, then use only `agent-loop delivery assignment retry --repo <path> --expected-generation <generation> --confirm-retained-fence --json`. The command may retry only the exact saved target and must reject a changed fence, target, generation, active worker, or repository. Never delete or edit the fence, transaction, assignment config, plist, state, lease, or worktree to force recovery.

Host delivery is separate from repository monitoring. Use `agent-loop delivery status --json` and `delivery check --json` for inspection. The only configuration authority is `$HOME/.agent-loop-delivery.yaml`; never add delivery keys to `.agent-loop.yaml`, store credentials there, or pass a non-default config to the LaunchAgent. `delivery configure` is a preview until the user explicitly authorizes `--apply`. Major, schema-changing, downgrade, same-version/different-commit, and unknown-protocol results remain blocked even for manual `delivery apply`.

Do not poll Releases or orchestrate update phases in Codex. `com.codex-issue-loop.delivery` owns the host lock, durable transaction, maintenance fence, drain, verified candidate, doctor/soak, and rollback. During `draining`, do not stop or signal workers; wait for their durable checkpoint or the configured defer result. If status reports `rollback_failed`, preserve the fence and backup path, show the non-destructive remediation, and never delete the fence, state, registry, worktree, lease, session, or pending request to force normal processing to resume.
